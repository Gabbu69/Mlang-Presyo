## Concrete findings and implemented fixes

1. **A pending save could close the wrong route.** Start a price save, open inline
   Add store while the write is pending, then let the save finish. The original
   form's navigation completion could close the newer catalog route and leave
   the original form showing Saving. The shared AppPage now blocks pointer and
   keyboard interaction and system/app-bar back while busy. Catalog, price, list,
   item and purchase forms, plus pending list duplication, use that guard.
   Async catalog/date callbacks also check that their context remains mounted.
   Affected areas: `lib/features/common.dart` and the five editing flows.
   Regressions: `in-flight price save blocks inline creation and system back until
   completion`; `in-flight linked purchase blocks back and records one atomic
   purchase`. Existing failed-write draft/retry assertions remain.

2. **A hidden manual estimate could survive a quantity change.** Start with a
   manual estimate, switch to Not estimated yet, change the quantity, then switch
   back to Manual. The hidden controller previously retained the old amount and
   could submit it as reconfirmed. ItemForm now clears that draft on every
   quantity/unit change, including while another estimate mode is selected.
   Affected area: `lib/features/lists.dart`. Regression: `changing quantity while
   a manual estimate is hidden requires reconfirmation`.

3. **Home and Lists could show the wrong newest list.** Valid ISO UTC timestamps
   can have different fractional precision; a string comparison can put an
   earlier instant ahead of a later one. Both screens now compare parsed instants
   and use a stable ID tie-breaker. Affected areas: `lib/core/domain.dart`,
   `lib/features/home.dart`, `lib/features/lists.dart`. Regressions include
   `Home and Lists show the actual newest restored shopping list` and the pure
   `updated_rows_test.dart` ordering cases.

4. **A committed write could be offered for replay after a failed reload.** A
   successful Duplicate followed by a database read failure previously looked
   like a failed save. Retrying could create another copy. The controller now
   distinguishes a write failure from a committed write needing a fresh read.
   It retains the last snapshot, blocks further writes, and returns stale detail
   routes to a recovery screen whose Retry performs only the read. Write failures
   still preserve the draft. Affected areas: app controller/shell and shared
   change handling. Regressions: `a committed duplicate is not replayed after its
   refresh fails`; `saved-refresh recovery retries reads without repeating the
   action`; `a failed post-commit refresh closes a stale detail route safely`;
   `demo refresh recovery retains the fictional-data banner`.

5. **Accepted records could exceed complete-backup capacity.** Settings and
   monthly-budget changes did not consistently enforce the aggregate row limit;
   individually valid Unicode notes could also make the exported UTF-8 document
   exceed 10 MiB. Repository writes and replacement restores now check the
   complete logical notebook's portable capacity before mutation, reserving the
   longest supported export timestamp. Existing entries remain editable at the
   row limit when the change stays within capacity. Affected areas: repository,
   validation and portability. Regressions: `settings and monthly budgets preserve
   the aggregate portable row limit`; `valid Unicode notes cannot make a
   successful write unbackuppable`.

6. **A selected-price snapshot could omit identity/provenance fields.** A
   hand-edited format-1 backup could previously omit fields needed to explain a
   detached frozen estimate. Validation now requires the complete basis already
   emitted by the app, including product identity, quantity kind, category,
   brand/variant, store identity, offer type and source. Empty brand/variant values
   remain valid present fields. Deleting a source quote still preserves the
   frozen basis and permits later recalculation. Affected area:
   `lib/data/validation.dart`. Regressions: `format 1 requires every field of the
   exported selected-price basis`; `selected-price basis rejects mismatched
   identity and quantity kind`; `a deleted source preserves a complete portable
   frozen basis`. Complete backups exported by 0.1.0 retain the same format.

7. **Backup confirmation required checked native write completion.** The export
   path now uses a small Android method-channel writer with the system document
   destination picker. It confirms success only after write, flush and close all
   complete. Cancellation returns without confirmation; permission, missing
   stream and I/O failures are reported without private provider paths. Activity
   destruction and worker completion cannot reply twice. Backup-first restore
   stops if export is canceled or fails. Affected areas: MainActivity,
   CheckedExportWriter, Dart ExportWriter and Settings. Regressions include
   `backup-first canceled export preserves the real notebook and stops restore`,
   its failed-export counterpart, `canceling the restore preview never invokes
   export or replacement`, and JVM cases for write/flush/close failure and closure
   order.

8. **Lazy search-field disposal could hide an active query.** On the TECNO KL7,
   enter a unique query in the 2,000-record fixture, dismiss focus, scroll the
   field out of the lazy list's retained area, then return and clear it. The
   field's local controller had been recreated empty while the Prices filter
   retained its query, so clearing the apparently empty field did not restore
   all records. PricesPage now owns and disposes its TextEditingController,
   keeping displayed text and active query consistent across child recreation.
   Affected area: `lib/features/prices.dart`. Regression: `search survives
   disposal of its unfocused lazy text field and can clear`, which verifies the
   original EditableTextState is disposed, a new one is created, the query is
   retained and clearing restores all records. Phone integration assertions were
   retained and an explicit retained-query assertion was added.

The phone integration workflow also now uses the separate package
`app.presyomlang.personal.integration`. Its script checks that identity before
Flutter testing, rebuilds and checks the normal package afterward, and uses a
direct ADB update without automatically uninstalling the personal notebook.
Integration databases remain test-owned temporary files. The first package guard
caught an uppercase Gradle-flag mismatch before any installation. After that
correction, the isolated package identity was verified and installed in 9.7
seconds. This does not establish normal personal-app installation or full suite
completion.
